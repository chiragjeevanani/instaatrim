1. EXECUTIVE PLATFORM ARCHITECTURE
================================================================================

1.1 Ecosystem Overview & The 3 Actor Panels
InstaaTrim is an on-demand and scheduled salon & grooming marketplace platform 
operating across three synchronized surfaces:

1. CUSTOMER PROGRESSIVE APP (`/customer/*`):
   - Mobile-first web/PWA interface for discovering nearby verified salons, 
     browsing services by gender/category, locking instant or scheduled slots, 
     purchasing Elite VIP passes, managing bookings, and submitting reviews.

2. SALON PARTNER PORTAL (`/salon/*`):
   - Tablet/Mobile/Desktop operations portal for salon owners and desk managers.
   - Manages live floor capacity (chairs/workstations), stylist attendance and 
     skill assignments, instant walk-ins, online booking lifecycle (Check-in, 
     Start Service, Complete), salon offers, customer review replies, and payout 
     withdrawal requests.

3. SUPER ADMIN CONSOLE (`/admin/*`):
   - Central command center for platform operators.
   - Manages salon verification & KYC approvals, commission splits, platform 
     taxes & convenience fees, financial payout clearance with Bank UTR reference 
     tracking, marketing/ad campaigns across 7 consumer touchpoints, editorial CMS, 
     global promo coupons, and customer dispute resolution tickets.

1.2 Architectural Paradigms & Tech Stack Expectations
- Standard RESTful JSON APIs communicating over HTTPS.
- Stateless token-based authentication (JWT with Access & Refresh tokens).
- Concurrency-safe slot reservation system using TTL-based cache or Redis locks.
- Real-time updates delivered via WebSockets or Server-Sent Events (SSE).
- Relational (PostgreSQL / MySQL) or Document (MongoDB) database supporting ACID 
  transactions for financial ledgers, booking status transitions, and wallet updates.

1.3 Real-Time State Synchronization Model
When an event occurs on any one panel, the other panels must reflect the update 
immediately:
- Customer creates booking -> Salon portal plays notification chime, increments 
  upcoming booking badge, and recalculates available chairs.
- Salon clicks "Check-In" / "Service Started" -> Customer booking screen updates 
  live step indicator; Chair is marked "Occupied" on both salon & public counters.
- Salon requests Payout -> Admin Sidebar displays pending settlement badge; 
  Admin ledger shows withdrawal request.
- Admin approves Payout with Bank UTR -> Salon Payouts ledger immediately shifts 
  status from "Pending" to "Transferred".
- Customer submits Star Rating & Review -> Appears on Salon Reviews page for 
  partner reply and Admin Reviews page for moderation.

2. ACTOR ROLES, AUTHENTICATION & RBAC PERMISSIONS
================================================================================

2.1 Actor 1: Customer (Client User)
- Identifier: Mobile Phone Number (10-digit Indian standard)
- Auth Mechanism: OTP Verification (Mock code `123456` or SMS Gateway API).
- Optional Social Login: Google / Apple OAuth (delivers verified email & profile).
- Data Scope: Can only read/write their own bookings, addresses, profile, and tickets.
- Default Customer in Seed: Ananya Sharma (`cust-1`, Phone: `7000792773`).

2.2 Actor 2: Salon Partner (Merchant / Branch Manager)
- Identifier: Partner Login ID (e.g. `partner-luxe`, `partner-jawed`), registered 
  Mobile number, or registered Business Email.
- Auth Mechanism: Password authentication OR Mobile OTP.
- Data Scope: Scoped strictly to their own `salonId`. Cannot access another 
  salon's financial data, bookings, staff, or settings.
- Default Partners in Seed:
  * Luxe Glow Salon & Spa (`sal-1` / Login: `partner-luxe` / Pass: `luxe123`)
  * Jawed Habib Hair Lounge (`sal-2` / Login: `partner-jawed` / Pass: `jawed123`)
  * Naturals Beauty Care (`sal-3` / Login: `partner-naturals` / Pass: `naturals123`)

2.3 Actor 3: Super Admin (Platform Operator)
- Identifier: Admin Email (`admin@instaatrim.com`)
- Auth Mechanism: Secure Password (`admin2025`) with optional 2FA.
- Data Scope: Global unrestricted access across all tenants, financial ledgers, 
  user accounts, and platform configurations.

2.4 Session Tokens, JWT Architecture & Auth Headers
All authenticated API requests from frontend panels include the standard HTTP header:
`Authorization: Bearer <JWT_TOKEN>`

JWT Payload Specifications:
- Customer Token: `{ sub: "cust-1", role: "customer", phone: "7000792773", exp: <timestamp> }`
- Partner Token:  `{ sub: "sal-1", role: "partner", salonId: "sal-1", exp: <timestamp> }`
- Admin Token:    `{ sub: "admin-1", role: "super_admin", email: "admin@instaatrim.com", exp: <timestamp> }`

4. END-TO-END BUSINESS LOGIC & OPERATIONAL FLOWS
================================================================================

--------------------------------------------------------------------------------
FLOW 01: Customer Auth & Onboarding Flow
--------------------------------------------------------------------------------
1. User enters 10-digit mobile number at `/customer/auth`.
2. Backend generates a 6-digit OTP and dispatches via SMS Gateway (or returns in dev).
3. User enters OTP:
   - Backend verifies OTP.
   - If phone number exists in `customers` table: Fetch profile and issue JWT.
   - If phone does not exist: Automatically create new customer record with 
     default referral code (e.g. `NAME50`), blank profile, and issue JWT.
4. Client stores JWT in local secure storage.
5. User can view and update Personal Profile (Name, Email, Gender, DOB) anytime at 
   `/customer/profile` via `PUT /api/customers/profile`.

--------------------------------------------------------------------------------
FLOW 02: Geolocation, Search & Salon Discovery Flow
--------------------------------------------------------------------------------
1. On app open or on `/customer/location`, app requests GPS coordinates.
2. If GPS granted: Backend maps `(lat, lng)` via Haversine formula to return 
   salons sorted by distance (in km).
3. If GPS denied: Customer picks manual locality (e.g. "South Tukoganj, Indore").
4. Customer filters salons by Gender Category (`Women`, `Men`, `Unisex`), rating, 
   or searches specific treatments (e.g., "RICA Waxing", "Keratin Spa").
5. Real-time availability indicator badge on salon cards calculates:
   - If available chairs > 0: Display "Instant Seat Available".
   - If available chairs == 0: Display "Next slot: 11:30 AM".

--------------------------------------------------------------------------------
FLOW 03: Service Catalog & Cart Management Flow (Single-Salon Scoping)
--------------------------------------------------------------------------------
1. Customer opens a Salon Profile (`/customer/salons/:id`).
2. Catalog is browsed by category tabs (Hair, Facial, Spa, Waxing, Makeup, Nails).
3. User clicks "Add" on a service.
4. CRITICAL BUSINESS RULE (Defect D2 Guard):
   - A cart is strictly scoped to ONE salon at a time.
   - If the user adds a service from Salon B while their cart contains services 
     from Salon A, the frontend informs the user and resets the cart for Salon B.
   - Backend API MUST reject any booking payload containing service IDs from 
     multiple distinct `salon_id`s.

--------------------------------------------------------------------------------
FLOW 04: Concurrency Slot-Hold Engine (8-Minute Temporary Lock)
--------------------------------------------------------------------------------
To prevent race conditions where two customers book the same chair/stylist:
1. Customer clicks "Book Appointment", selects Date & Timeslot.
2. Frontend immediately calls `POST /api/holds` with `{ salonId, staffId, date, startMin, endMin }`.
3. Backend checks if `slot_holds` has an active non-expired record for that chair/slot.
4. If available:
   - Creates hold record with `expires_at = NOW() + 8 minutes`.
   - Returns `{ holdId: "hold-xxx", expiresAt: "..." }`.
   - Frontend starts an 8-minute countdown timer on screen (`HoldCountdown.jsx`).
5. If another customer attempts to pick the same slot during these 8 minutes, 
   the slot returns disabled (`isAvailable: false`).
6. If the 8-minute timer runs out before payment completion:
   - Hold status transitions to `expired`.
   - Checkout displays warning: "Held slot expired. Please pick a new one."
7. When the booking is successfully confirmed, the hold status transitions to 
   `confirmed` and binds to the booking record.

--------------------------------------------------------------------------------
FLOW 05: Instant Seat Booking vs Scheduled Timeslot Booking Flow
--------------------------------------------------------------------------------
The platform provides two distinct booking modes:

MODE A: "INSTANT CHAIR" (Walk-in / Immediate Visit)
- Available only during salon operating hours when `total_chairs - occupied_chairs > 0`.
- The customer books for immediate arrival ("Within 15 mins").
- Booking is immediately marked `Confirmed`.
- Salon receives instant notification sound: "New Instant Walk-in Chair Booking!".
- Station is temporarily reserved for 15 minutes awaiting customer arrival.

MODE B: "SCHEDULED TIMESLOT" (Advance Booking)
- Customer selects date from a 14-day rolling window (`rollingDays(14)`).
- Time slots are generated based on salon operating hours (e.g. 10:00 AM - 08:00 PM) 
  in 30-minute intervals.
- Slot availability engine checks:
  1. Salon operating hours for that day.
  2. Confirmed bookings during that window.
  3. Active holds during that window.
  4. Stylist / staff working roster.

--------------------------------------------------------------------------------
FLOW 06: Checkout, Coupons, Elite VIP Pricing & Payment Processing Flow
--------------------------------------------------------------------------------
1. Pricing Calculation Engine:
   - `Gross Subtotal` = Sum of all service prices.
   - `Coupon Discount` = Computed via promo rules (flat amount or percentage with cap).
     * Check rule: `firstBookingOnly` -> Verify `bookings.count(customerId) == 0`.
     * Check rule: `minOrder` -> Verify `Gross Subtotal >= coupon.minOrder`.
   - `Elite VIP Discount` = If `customer.isElite == true`, apply extra 10% discount 
     on the remaining balance.
   - `Convenience Fee` = ₹15 (Waived if customer is Elite VIP).
   - `GST Tax` = 5% of taxable base.
   - `Net Payable` = `Gross Subtotal - Discounts + Convenience Fee + GST`.
2. Payment Gateways:
   - Online: UPI (Google Pay, PhonePe, Paytm), Credit/Debit Card, Net Banking.
   - Offline: "Pay at Salon" -> Creates booking with `paymentStatus: "Pending"`.
3. Upon payment success:
   - Create record in `bookings` table.
   - Release / confirm hold in `slot_holds`.
   - Increment `coupon.usageCount`.
   - Send push & SMS booking confirmation to customer.
   - Broadcast `NEW_BOOKING` event to Salon Partner Portal.

--------------------------------------------------------------------------------
FLOW 07: Real-Time Booking State Machine (Canonical 8-State Engine)
--------------------------------------------------------------------------------
Both Customer App, Salon Portal, and Admin Console adhere to this strict lifecycle:

   [Pending] -----------> [Confirmed] -----------> [Cancelled]
                              |
                              +---------> [No Show] ------> [Refunded]
                              |
                              v
                        [Checked-In]
                              |
                              v
                     [Service Started]
                              |
                              v
                        [Completed] -------------> [Refunded]

State Actions & Floor Impact:
1. `Pending`: Payment confirmation pending (or unverified walk-in).
2. `Confirmed`: Chair reserved; displayed in Salon "Upcoming Bookings" list.
3. `Checked-In`: Customer arrives at salon; desk clicks "Check-In".
4. `Service Started`: Stylist begins work; desk assigns Chair & Stylist:
   - Chair status shifts to `is_occupied: true`.
   - Salon live occupied chairs counter increments.
   - Customer UI updates to "In Service".
5. `Completed`: Service finished; bill settled.
   - Chair status shifts back to `is_occupied: false`.
   - Revenue added to Salon Wallet available balance.
   - Customer UI prompts for Star Rating & Review.
6. `Cancelled`: Cancelled by customer or salon with mandatory reason.
7. `No Show`: Customer failed to arrive within 30 minutes of scheduled time.
8. `Refunded`: Settlement reversed via Admin or automated gateway refund.

--------------------------------------------------------------------------------
FLOW 08: Booking Rescheduling & Cancellation / Refund Flow
--------------------------------------------------------------------------------
RESCHEDULING:
1. Customer opens an upcoming booking and clicks "Reschedule".
2. Picks new date and timeslot.
3. Backend releases existing slot, checks availability for new slot, and locks it.
4. Booking record updates `dateKey` and `time` with status remaining `Confirmed`.

CANCELLATION & REFUNDS:
1. Customer clicks "Cancel Booking" and selects a reason.
2. Backend checks `platform_settings.cancellation_free_hours` (Default: 1 hour).
   - If slot time is > 1 hour away: Full 100% refund initiated to original payment source.
   - If slot time is < 1 hour away: Platform fee or late cancellation fee deducted.
   - If customer has Elite VIP Pass: Free cancellation guaranteed up to 1 hour.
3. Booking status shifts to `Cancelled`.
4. Associated chair and staff time freed up immediately.

--------------------------------------------------------------------------------
FLOW 09: Rating, Review & Salon Inline Reply Synchronization Flow
--------------------------------------------------------------------------------
1. Upon booking reaching `Completed` status, Customer App renders review modal.
2. Customer selects Star Rating (1 to 5), enters comment, and submits.
3. Frontend triggers `api.bookings.addRating` AND `api.reviews.add(salonId)`.
4. Backend creates record in `reviews` table and recalculates `salon.rating` & `salon.review_count`.
5. Review immediately appears in:
   - Salon Partner Portal at `/salon/reviews`.
   - Super Admin Console at `/admin/reviews`.
6. Salon owner clicks "Reply" on `/salon/reviews` and inputs a response.
7. Backend updates `review.reply = { text, repliedAt: NOW() }`.
8. The reply reflects in real-time under that review on public salon profiles.

FLOW 12: Salon Payout & Wallet Settlement Flow (GMV, Commission, UTR Clearance)
--------------------------------------------------------------------------------
1. Dynamic Wallet Balance Calculation:
   - `Total GMV` = Sum of all `final_paid` from `Completed` bookings for that salon.
   - `Platform Commission` = `Total GMV * (salon.commission_rate_percent / 100)`.
   - `Net Salon Earnings` = `Total GMV - Platform Commission`.
   - `Available Payout Balance` = `Net Salon Earnings - Sum(Settled & Pending Payouts)`.
2. Salon Requests Payout (`/salon/payouts`):
   - Salon enters amount (must be >= `platform_settings.min_payout_threshold`, default ₹1,000).
   - Submits withdrawal request.
   - Record created in `payouts` table with `status: "Pending"`.
3. Admin Settlement Workflow (`/admin/payouts`):
   - Admin sees pending request with Salon Bank Details and account number.
   - Admin processes bank transfer via NEFT / RTGS / IMPS.
   - Admin clicks "Clear", enters Bank UTR Reference Number (e.g. `HDFC0098231456`), and confirms.
   - Backend updates payout record: `status: "Transferred"`, `utr_number: "...", `clearance_date: NOW()`.
   - Salon portal ledger updates status immediately to "Transferred" with UTR number displayed.

6.1 WebSocket Rooms & Event Channels
Server should run a WebSocket / Socket.io server at `/ws` or SSE stream at `/api/events`:

Channel Rooms:
1. `room:salon:<salonId>`: Joined by Salon Partner desk tablets/browsers.
2. `room:customer:<customerId>`: Joined by Customer App sessions.
3. `room:admin`: Joined by Super Admin consoles.

Events Emitted:
- `booking:created` -> Dispatched to `room:salon:<salonId>` and `room:admin`.
- `booking:status_updated` -> Dispatched to `room:customer:<customerId>` and `room:salon:<salonId>`.
- `payout:requested` -> Dispatched to `room:admin`.
- `payout:cleared` -> Dispatched to `room:salon:<salonId>`.
- `review:added` -> Dispatched to `room:salon:<salonId>`.
- `chairs:updated` -> Dispatched to public listeners of that salon.

6.2 Scheduled Background Crons (Workers)
1. Slot Hold Reaper (Runs every 30 seconds):
   - Queries `slot_holds` where `status = 'active'` AND `expires_at < NOW()`.
   - Updates status to `expired`.
   - Frees up slot locks.
2. Appointment Reminder Worker (Runs every 15 minutes):
   - Finds confirmed bookings scheduled 1 hour from current time.
   - Dispatches SMS & WhatsApp reminders to customers with salon address and navigation link.
3. No-Show Auto-Marker (Runs every 30 minutes):
   - Flags bookings that were scheduled > 45 minutes ago and were never Checked-In as `No Show`.
4. Daily GMV & Financial Reconciler (Runs nightly at 00:05 AM):
   - Audits completed bookings, computes platform commissions, and updates salon earnings ledger.

6.3 Third-Party Webhook Handlers
- `POST /api/webhooks/razorpay` (or Stripe / Cashfree):
  * Handles asynchronous payment confirmation, chargebacks, and refund settlements.
- `POST /api/webhooks/whatsapp` (Gupshup / Twilio / Wati):
  * Handles message delivery receipts and customer replies.

7. BUSINESS CONSTRAINTS & AUDIT CHECKLIST FOR BACKEND IMPLEMENTATION
================================================================================

[ ] Single-Tenant Cart Validation: Reject any checkout request where items span 
    more than one `salon_id`.
[ ] Atomic Concurrency Holds: Use database row locking (`SELECT FOR UPDATE`) or 
    Redis key with TTL to guarantee no double-booking of a stylist/chair.
[ ] Idempotent Payment Processing: Payment webhook must check if booking is 
    already confirmed before processing to prevent duplicate bookings on network retries.
[ ] Wallet Integrity: Available payout balance must NEVER become negative. Validate 
    balance before creating payout record.
[ ] Review Authenticity: Customers can only review salons for which they have a 
    record in `bookings` with status `Completed`.
[ ] Strict Timezone Consistency: All dates and times must be stored in UTC in the 
    database, and formatted in Indian Standard Time (IST / UTC+05:30) for display.
[ ] Passwords & Security: Salon partner passwords and admin credentials must be 
    hashed with Bcrypt (cost factor >= 10). Never store plain text passwords.
